## 6. 드래그 편집 구현 구조

| 계층 | 파일 | 역할 |
|---|---|---|

규칙:
- **첫 칸은 기존 클릭 규칙 그대로**(같은 종류면 제거/방향 순환/초기 상태 순환, 다른 요소 덮어쓰기, 시작점·마지막 목표 보호).
- **이어지는 칸**: 첫 칸이 같은 종류였으면 같은 종류만 지우는 "제거 스트로크", 아니면 **빈 칸에만** 배치. 드래그 경로 위의 다른 요소를 실수로 덮어쓰지 않는다. 지우개는 보호 대상(시작점·마지막 목표)을 건너뛴다.
- 연속 배치 대상: 벽·목표·폭탄·부서지는 바닥·단방향·토글 벽·지우개. **시작점·포털·스위치는 한 칸만**(연결 관계가 드래그로 퍼지지 않도록). 토글 벽 드래그는 시작 시점의 그룹 ID 하나로 문 한 줄을 만든다.
- 같은 스트로크에서 방문한 셀은 `visited`로 한 번만 처리 → 토글 벽이 한 드래그에서 여러 번 반전되지 않는다.
- 빠른 이동으로 건너뛴 셀은 Bresenham 보간.
- 드래그 중에는 지역 미리보기 초안만 갱신(새 셀을 지날 때만 React 갱신), **포인터 업에서 History에 1회 커밋 → Undo 1회 = 드래그 1회**, Redo 정상.
- 미리보기와 확정 상태는 같은 초안 객체이므로 불일치가 없다.
- 취소: `pointercancel`, Escape, Space+드래그 팬, 두 번째 손가락(핀치) → 스트로크를 **폐기**(반쯤 적용하지 않음).
- 모드 구분: 선택 모드 = 요소 이동(기존 `useElementDrag`), 그리기 모드 = 연속 배치, Space+드래그·가운데 버튼·두 손가락 = 화면 이동/확대.
- 모바일: 그리기 도구에서 **"터치 그리기"** 토글. 끄면 탭 = 한 칸 배치, 한 손가락 끌기 = 스크롤; 켜면 한 손가락 끌기 = 연속 배치(`touch-action: none`). 두 손가락은 항상 확대·이동.
- 키보드(Enter/Space) 셀 활성화는 그대로 동작한다. `GridSvg`가 키보드 활성화에 `'keyboard'` 출처를 넘겨, 포인터 스트로크용 클릭 흡수가 키보드 입력을 먹지 않는다.

브라우저 검증 중 발견·수정한 결함 2건:
1. 스트로크의 포인터 캡처 때문에 뒤따르는 click이 셀이 아닌 곳으로 갈 수 있어, 남은 흡수 플래그가 다음 **선택 모드** 클릭을 삼켰다(기존 E2E 2건 실패로 발견). → 현재 모드의 훅만 클릭을 흡수, 캡처는 셀에.
2. 흡수 시간창(500 ms)을 포인터 다운에서 시작해, 500 ms 넘는 드래그는 끝난 뒤 click이 **첫 칸을 다시 토글**했다(64×64 E2E에서 58/59로 발견). → 시간창을 스트로크 종료 시점에 시작. 회귀 단위 테스트 추가.

## 9. 토글 벽 초기 상태 모델

- 데이터: `ToggleWallTile { x, y, groupId, initialOpen? }`. `false`는 저장하지 않는다(닫힘 = 기존 벽과 바이트 동일).
- 규칙: **벽의 현재 상태 = `initialOpen` XOR (그룹이 홀수 번 토글됨)**. 스위치는 그룹의 모든 벽을 "자신의 현재 상태에서" 반전한다.

| 상태 | 문 A (초기 닫힘) | 문 B (초기 열림) |
|---|---|---|
| 초기 | 닫힘 | 열림 |
| G1 1회 | 열림 | 닫힘 |
| G1 2회 | 닫힘 | 열림 |

- 상태 키: 기존 `toggleMask`(그룹 패리티) 그대로. 초기 상태는 정적 설정이므로 패리티 + 설정으로 모든 문이 결정된다 → **새 상태 비트 불필요, 서로 다른 동적 상태가 같은 키로 합쳐지지 않음**(같은 칸·다른 패리티 → 다른 키를 테스트).
- `openGroups`의 의미는 "홀수 번 토글된 그룹"으로 유지하고, 렌더러(`FeatureOverlay`, `GridSvg` 접근성 설명)와 엔진 모두 `toggleWallOpen()` 한 함수를 쓴다. 편집기 미리보기·직접 플레이·학습 환경이 같은 계산을 공유한다.
- 초기 열림 벽은 오른쪽 위 삼각 표식으로 표시되어, 토글 후에도 "반전된 문"을 구별할 수 있다.
- 편집: 토글 벽 도구로 같은 벽 재클릭 → 초기 상태 순환(빈 칸 클릭 → 닫힌 벽 생성). 인스펙터 버튼. 이동·삭제·Undo/Redo·JSON에서 보존.

## 16. 성능 측정

`npm run benchmark`(Edge headless, 1366×768, dev 서버)를 V4와 V3 기준(`1acad4a`, 임시 worktree)에서 순차 실행. 원시 결과: `benchmarks/results/v4*.json`, `v4-baseline-1acad4a*.json`.

**엔진 장기 실행**(동기 500,100 스텝, UI 구독 없음): 9개 프리셋 모두 궤적 동일. steps/s 평균 V4 226,237 / V3 180,508 — 첫 프리셋(01: 490,869 vs 193,760)의 JIT 워밍업 차이가 평균을 끌어올리므로, 이는 "저하 없음"으로만 해석한다(나머지 프리셋은 ±15% 범위).

**대형 맵 SVG**(정책·가치 오버레이 포함, 2 s 학습, 단발 측정):

| 맵 | 초기 렌더 ms V4/V3 | 100k 전이 ms V4/V3 | 프레임 p95 ms V4/V3 |
|---|---|---|---|
| 20×20 | 33 / 65 | 84 / 247 | 38 / 77 |
| 32×20 | 53 / 49 | 115 / 244 | 55 / 89 |
| 48×40 (30번) | 100 / 163 | 157 / 363 | 60 / 79 |
| 64×64 | 143 / 395 | 127 / 249 | 106 / 111 |

단발 측정 편차가 크다(같은 코드 반복 시 48×40 렌더 91–198 ms 범위). 결론은 "V3 대비 회귀 없음"까지만 주장한다.

**판단을 바꾼 측정**: 드래그 꼬리 지연을 줄이려고 셀 단위 `memo` 컴포넌트를 도입했으나(64×64 드래그 p95 28–31 → 18 ms), 같은 벤치에서 48×40 초기 렌더가 341–439 ms(memo 이전 73–76 ms)로 악화되어 **되돌렸다**. 최종 코드의 64×64 드래그는 새로 지난 셀당 React 렌더+커밋 중앙값 10–21 ms, p95 12–25 ms(두 차례, 프로덕션 빌드).

64×64 편집: 59셀 직선 스트로크가 정확히 59개 벽으로 확정(한 드래그 = Undo 1회는 7×7 단위·E2E 테스트에서 검증). 순수 연산으로 64×64에 3,000+ 셀 지그재그 스트로크가 5 s 한도 안에 처리됨(단위 테스트).

## 17. 남은 문제 및 제한

- **주관적 디자인 평가**(객관 테스트와 별개): 인스펙터는 기존 패널 토큰(세이지 그린, 1px 테두리, 그림자·그라데이션 없음)을 따르고 선택 즉시 위치를 알 수 있다. 다만 모바일에서는 인스펙터가 격자 아래 시트라 긴 그룹 목록에서 스크롤이 필요하다. 툴바는 기존 그대로라 모바일에서 화면 상단을 많이 차지한다(V4 범위 밖, 변경 안 함).
- 데스크톱 Edge가 `maxTouchPoints > 0`을 보고하는 환경에서는 "터치 이동/터치 그리기" 버튼이 데스크톱에도 보인다(기존 "터치 이동"과 같은 동작).
- 지우개 드래그가 시작점을 지날 때 보호 메시지는 스트로크가 다른 칸을 바꾼 경우 편집기의 "초안 변경 시 메시지 초기화" 동작 때문에 표시되지 않는다(데이터는 올바르게 보호됨).
- 실제 손가락 드래그는 Playwright에서 합성 Pointer 이벤트로 검증했다. 실기기 수동 확인은 하지 않았다.
- `catalog.spec.ts` 홈 시연 테스트는 전체 실행 부하에서 간헐 실패 가능(§15).
- 벤치는 단발 측정이 섞여 있어 작은 차이는 의미가 없다.
