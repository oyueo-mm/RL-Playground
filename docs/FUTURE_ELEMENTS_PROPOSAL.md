# 향후 환경 요소 제안 — 늪/험지, 단방향 포털

> 상태: **검토 문서. V4에서 구현하지 않았다.** 기존 포털·타일 규칙은 바꾸지 않았다.
> 근거 코드: `src/core/environments/gridworld/GridWorldEnv.ts`, `features.ts`, `types.ts`, `src/viz/controls/envEditorIO.ts` (V4 기준).

## 공통 전제 (V4 시점 엔진)

- 상태 키: `"x,y,goalMask"` 또는 동적 요소가 있으면 `"x,y,goalMask,fragileMask(16진),toggleMask(16진)"`.
- 보상 결정 순서(`step()`): 단방향 출발 제한·붕괴·닫힌 토글 벽 → 경계 → 정적 벽 → 폭탄 → 목표 → 일반 이동.
- 포털은 **목적지 셀에 진입하는 순간** 반대쪽 끝으로 순간 이동하며, 양방향 인덱스(`portalIndex`)에 두 방향을 모두 등록한다.
- 내보내기 스키마: v2(특수 요소), v3(V4 개별 보상·초기 문 상태). 새 필드는 "필요할 때만 상위 버전" 원칙을 따른다.

## 후보 A. 늪 / 험지 (Terrain Cost)

**규칙 제안.** 통과 가능한 셀. 그 셀에 **진입**하는 이동의 보상이 `stepReward` 대신 셀의 `cost`(음수 권장, 유한 실수)가 된다. 이동 자체·종료 규칙은 일반 칸과 같다.

| 항목 | 분석 |
|---|---|
| 교육적 장점 | 최단 경로(스텝 수)와 최대 누적 보상 경로가 갈라지는 상황을 직접 만든다. γ, stepReward, cost의 상호작용(우회 vs 관통)을 Q값/정책 오버레이로 비교하기 좋다. |
| 데이터 구조 | `GridFeatures.terrains?: { x, y, cost?: number }[]`. `cost` 생략 시 맵 단위 `terrainCost`(신규, 기본 예: -1)를 상속 — V4의 `goalReward`/`reward` 상속 패턴과 동일. |
| 엔진 수정 범위 | `indexConfig()`에 `terrainCosts: Map<key, number>` 추가, `step()`의 마지막 일반 이동 분기에서 `terrainCosts.get(key) ?? stepReward`. 한 번의 Map 조회라 핫패스 비용은 V4 개별 보상과 같은 수준. 포털 목적지가 험지일 때 **도착 셀** 비용을 쓸지 정책 결정 필요(제안: 도착 셀). |
| 상태 공간 | **변화 없음.** 비용은 정적 지형이므로 상태 키에 비트를 추가하지 않는다. `stateSpaceEstimate` 수식도 그대로. |
| 프리셋 호환 | 기존 30개 맵은 `terrains`가 없으므로 동작 동일. 내보내기는 `terrains` 존재 시에만 v4 스키마. |
| 렌더링/편집 | 셀 배경 패턴(물결) + 맵 보상 숫자 레이어에 비용 표시. 드래그 연속 배치 대상(`PAINTABLE_TOOLS`)에 바로 편입 가능. 인스펙터는 목표/폭탄의 "기본값 사용/개별 값" UI를 재사용. |
| 위험 | 비용이 양수면 "보상 타일"과 사실상 같아져, 제거된 `rewardTiles`의 반복 수집 문제(무한 보상 루프)가 재발한다. → **cost ≤ 0만 허용**하거나 양수 경고 필요. |

## 후보 B. 단방향 포털 (Directed Portal)

**규칙 제안.** 입구 A에 진입하면 B로 이동하지만, B에 진입해도 A로 가지 않는다(B는 일반 칸처럼 동작하거나, 별도 표시된 "출구"). 기존 양방향 포털과 공존.

| 항목 | 분석 |
|---|---|
| 교육적 장점 | 되돌아올 수 없는 선택(비가역 전이)을 만든다. 탐험 중 함정 같은 상태 전이, 할인율에 따른 지름길 선호를 실험하기 좋다. |
| 데이터 구조 | 하위 호환을 위해 기존 `PortalPair`에 선택 필드 `directed?: true` 추가(ends[0]→ends[1]만 연결). 별도 배열보다 ID 고유성·편집 UI·검증(`ends.length === 2`)을 그대로 재사용할 수 있다. |
| 엔진 수정 범위 | `indexConfig()`의 `portalIndex` 생성 시 `directed`면 `ends[0]→ends[1]`만 등록. `step()`은 변경 없음. 렌더 모델은 `features.portals`를 그대로 전달하므로 렌더러가 방향 화살표만 그리면 된다. |
| 상태 공간 | **변화 없음.** 정적 연결이다. 단, 도달 불가능 영역이 생길 수 있어 프리셋 감사(`audit.ts`)의 "목표 회수 불가 상태" 검사가 의미 있어진다. |
| 프리셋 호환 | 기존 포털은 `directed`가 없으므로 양방향 유지. 스키마는 `directed` 사용 시에만 상위 버전. |
| 렌더링/편집 | 입구 ◎, 출구 ◉(또는 화살촉)로 구별하고 선택 시 연결선에 화살표 마커. 인스펙터에 "양방향 / A→B 단방향" 세그먼트 버튼과 "방향 뒤집기". |
| 위험 | B가 다른 포털의 끝점이거나 B에 들어가자마자 다시 텔레포트되는 체인은 현재도 막혀 있다(한 번만 텔레포트). 이 규칙을 문서화하고 테스트로 고정해야 한다. |

## 권장 순서

1. **단방향 포털** — 엔진 변경이 인덱스 생성 한 줄 수준이고 상태 공간 영향이 없으며 기존 포털 UI를 재사용한다.
2. **험지** — 보상 정책(cost 부호 제한, 포털 도착 셀 비용)을 먼저 결정한 뒤 구현한다.

두 요소 모두 구현 시에는 기존 30개 프리셋 성공 경로 재생 테스트(`validateSolutions.test.ts`)와 내보내기 바이트 동일성 테스트(`elementProperties.test.ts`)를 그대로 통과해야 한다.
